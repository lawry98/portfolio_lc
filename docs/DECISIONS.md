## D-21 · T12 scroll bounds: two furniture-inset stages from one rule, a CSS-px WebGL scissor clip on both renderers, containment clamping at the home-pin seam, and a subscription-only hand-off fade — 2026-09-01

**Choices:** (1) **One rule generates both stages (R12-6, R12-9):** `src/pet/stage.ts` is a new **PURE** geometry core in the `anchor.ts`/`fsm.ts` mould (136 lines, **zero imports** — no gsap, no three, no DOM, no `window`, no clock, no `Math.random`; grep-verified by the reviewer rather than taken from the report): `stageFromSection(section, furniture)` returns the section's own box with only `height` changed — bottom-inset to the **topmost** furniture rect, clamped to the section's own bottom, floored at 0, and a no-op on an empty furniture list; `intersectViewport(stage, viewport)` clips to the on-screen rect and returns **`null`** for any zero-or-negative-area overlap, which is the render-skip signal; `clampToStage(point, size, stage, pad)` contains a box **centre**. Hero and footer stages are the *same call with different inputs* — the hero clears `.hero__scroll`, the footer clears `.footer__meta` + `.footer__copyright` — because the furniture is **declared in the markup** as `data-byte-furniture` (three elements, the only page-level change T12 makes) rather than named by CSS class inside `pet/`, which would cost the module its page-independence (R12-6 — it is why `index.html` joins the file list). The footer's section lookup must be **`closest('section, footer')`, not `closest('section')`** (R12-9): `<footer id="footer">` is a `<footer>` tag and a **sibling of `<main>`** (its `class="section"` is CSS only), so the bare selector returns `null` and the footer stage would silently never exist — a failure with no error message. The pre-existing bare `closest('section')` in `feedZone` (`createBytePet.ts:368-369`) is deliberately left alone: it only ever sees the hero headline. (2) **The scissor takes CSS px, not device px (R12-1):** the ticket said device px; three@0.185.1 multiplies `setScissor` by the renderer's pixel ratio **internally** (`three.cjs:76805`), so device px would clip to a **quarter-size** region on any retina display. `scene.ts` therefore passes CSS px, matching `applyViewport`'s own `setSize`. The Y flip (GL's origin is bottom-left, the DOM's is top-left) is `glY = viewportHeight - (stage.y + stage.height)`, extracted after review into an **exported pure `scissorFromStage(stage, viewportHeight)`** beside `worldFromScreen` (+5 unit tests) so the arithmetic is testable without a GL context. (3) **Clear order is the whole correctness story (R12-2 + R12-3):** every frame both renderers take a **full clear with the scissor test OFF**, then the scissor box, then `render()`; when the active stage is `null` both canvases are still **cleared** and both draws skipped. Skipping `render()` alone freezes the last frame on the compositor (R12-3 — precisely the bug T12 exists to fix), and clearing *inside* the scissor leaves the previous stage's pixels behind when the box moves (R12-2). Neither was left as reasoning: a standalone WebGL2 context at **DPR 2** showed a scissored `clear()` leaving the prior stage's band on screen, and showed the flipped band's edges landing on DOM y **85** and **805** to the pixel. (4) **`setStage` is tri-state, not boolean (R12-4):** `undefined` = never configured → render unclipped (byte-identical to pre-T12, so `createScene` stays non-breaking for any caller that never calls it); `null` = clear-and-skip; a rect = clip. It ships alongside a new `SceneHandle.setOpacity(a)`. (5) **Containment clamps at the `onTick` home-pin seam, not in `feed.ts` (R12-7):** `feed.ts` is outside the ticket's file list, and the scissor is design row 5's stated backstop for the dash, so the clamp guards the steady-state hard-pin and the no-snap reacquire target — both of which consume the same `rootX`/`rootY` — while a dash may still reach the clip edge by design. `clampToStage` takes a box **centre** where `onTick` writes Byte's **feet**, so that conversion lives in an exported pure `clampFeetToStage` in `scene.ts` (+6 tests, extracted in Task 3's fix round beside `scissorFromStage`; its no-op round-trip test was checked to genuinely fail if a conversion were dropped or doubled). **Owner-visible:** the clamp is a **complete no-op at 1440×900** at both homes — Byte's resting position is byte-identical to pre-T12 — and the **footer never clamps at any viewport**; but on narrower viewports it pulls the **hero** anchor left, **−23px at 768×1024** and **−14px at 390×844**, because the bound is the **section** box (which excludes the scrollbar), not the viewport. That is required, not incidental: at 768 the hero section is 753 wide, so unclamped Byte's right edge lands 11px past it and the scissor would visibly **slice** Byte. The chosen edge behaviour (design demo option **C**) is explicitly "the clip stays as a backstop that never fires", which means clamping the base anchor and not just the wander. **`STAGE_CLAMP_PAD_PX` (12) is the single tunable** if the owner wants Byte to rest further out. (6) **The hand-off fade is a GSAP opacity tween on the two canvas elements, subscription-only (R12-5):** no rig/shadow opacity API exists and the ticket excludes `rig.ts`/`shadow.ts`, so the new `SceneHandle.setOpacity` drives the canvases — the right blast radius, since those canvases carry only pet output. `createBytePet` tweens **1→0→1** across the hero↔footer hand-off over `STAGE_FADE_DURATION_S` (0.3s), wired through the FSM's existing `fsm.onEnter` (a **subscription only** — no FSM edit). **The fade is not the guarantee; the scissor is.** The implementer's original "safe because opacity is ~0 throughout traveling" rationale was **ruled false** in review: the fade-out ramps from 1 over 0.3s, and `fsm.ts:388`'s `traveling --FEED--> dashing` edge restores opacity to **1** for seconds mid-trip. The conclusion survived (the clip is unconditional), but the rationale was corrected in the report **and** in the code comments (`createBytePet.ts:1633-1643`, `scene.ts:121-130`) so that no future reader deletes the clip believing the fade protects them. (7) **`fsm.ts` and all T8 migration logic stay untouched (design row 4):** lane travel becomes invisible for free once the clip exists — verified across the whole branch, with `fsm.test.ts` (1103 lines) passing unchanged. Measurement rides the **existing** `onTick` read batch (both section boxes + their furniture, every tick — no second scroll listener, matching how T8's live `pickAnchor` already works), the active stage follows `activeHome`, and reduced motion keeps **both** the clip and the fade (opacity-only is the reduced-motion-safe idiom, and `runMigrationReduced` already snaps without a lane). (8) **Branch base = `4288559` (R12-8):** not `feat/byte-pet-demo` @ `9151ebe`, whose extra commit is another agent's colliding T12 docs ticket; basing on the T10 close keeps this ticket's history clean, at a cost of at most a trivial docs merge for the owner.
**Why:** the two canvases are full-viewport `position: fixed`, so before T12 nothing bounded them and T8's right-margin lane traversed APPROACH in plain sight. Deriving a stage from the section the pet belongs to — and enforcing it with the **scissor test** — fixes that at the lowest level available: a GPU-level clip is a guarantee no *future* pet feature (a longer dash, a new wander, a stray particle) can escape, whereas any position-only fix would have to be re-proved for every drawing Byte ever gains. Keeping the geometry pure and the FSM untouched means the whole rule is unit-testable and costs T8 nothing; declaring furniture in markup keeps `pet/` mountable in the Next.js portfolio unchanged. **No new runtime deps. No `src/` file outside `pet/` changed** (the only page edit is three `data-byte-furniture` attributes). Created `src/pet/stage.ts` + `stage.test.ts`; modified `scene.ts`, `scene.test.ts`, `createBytePet.ts`, `types.ts`, `index.html` — **928 insertions across 7 files**. JS **209.55 KB gz** (T10: 206.40; **+3.15**) / CSS **3.33 KB gz** / fonts **26.15 KB** unchanged — all far under the SPEC §13 budgets (280 / 20). **285 tests** (+35 vs T10's 250: **24** `stage.test.ts`, **5** `scissorFromStage`, **6** `clampFeetToStage`); `npm test`, `npm run lint`, `npm run format:check`, `npm run build` all clean. Executed via `subagent-driven-development`: 3 implementation tasks + per-task reviews (Task 1 clean — spec ✅, quality Approved, 0 Critical/Important; Task 2 Approved-with-1-Important → 1 fix round extracting `scissorFromStage` → scoped re-review ADDRESSED; Task 3 Approved-with-1-Important → 1 fix round extracting `clampFeetToStage` + the fade-vs-clip rationale correction → scoped re-review ADDRESSED) + this docs task, with **three reviewer ⚠️s closed by the controller with evidence rather than argument** (the uncommitted `TICKETS.md`/demo files provably predating the branch; the retina + ghosting claim, settled by the live DPR-2 GL proof; the footer anchor's clearance, settled by measuring the real anchors with the Range-based text measure the code itself uses — the footer clamps zero on both axes everywhere). QA: **78 scroll positions × 3 viewports, zero overlaps**, run against the real shipped `stage.ts` imported as an ES module — full record in [`PROGRESS.md`](PROGRESS.md); the *animated* pass (hand-off fade on screen, mid-trip feed, occlusion weave, FED counter, reduced-motion on device) is an **owner/on-device residual**, the same limitation T10 recorded in `docs/qa/README.md` §4. Rulings **R12-1** scissor takes CSS px · **R12-2** scissor-off full clear before every clipped frame · **R12-3** the null-stage skip path still clears · **R12-4** tri-state `setStage` · **R12-5** hand-off fade via `SceneHandle.setOpacity` on the canvases · **R12-6** furniture declared in markup (`data-byte-furniture`) · **R12-7** clamp at the `onTick` home-pin site, not `feed.ts` · **R12-8** base on `4288559` · **R12-9** `closest('section, footer')` for the footer stage. ## D-20 · Footer feeding: the feed zone FOLLOWS the active home (region tags, not page classes) — 2026-09-01
**Choices:** (1) **The zone is re-bound on every home switch, not captured at construction.** `createBytePet`'s `feedZone` was a `const` derived once from `opts.headlineEl` — the HERO headline — so the module's only `pointerdown` listener stayed pinned to `#hero` for the whole page life. `setHomeAnchor` moved the anchor, the caret, the retype target and the phrase cycle, but not the zone, so once Byte migrated to the footer, clicking or tapping the footer fed it nothing while the footer home, the `phrases.footer` cycle and the `[data-fed-counter]` counter all sat there working. This is not a tuning miss but a routing impossibility: a page's footer is a SIBLING of its hero (`footer#footer < div#app < body`), so a footer `pointerdown` never bubbles through a hero-pinned listener. `feedZone` becomes a `let` owned by `bindFeedZone`/`unbindFeedZone`; `setHomeAnchor` re-points the single listener (idempotent, so a host page whose two homes resolve to ONE region — or a redundant switch — never churns listeners), and `destroy()` releases whichever zone is bound instead of assuming the hero. (2) **The derivation moves to a PURE `pet/feedZone.ts`** — the same pure-core/executor split as `anchor.ts`/`retype.ts` — so "which region owns this home?" is jsdom-testable without a scene, a ticker or a browser. (3) **Region TAGS, never page CSS class names** (`section, article, aside, nav, header, footer, main`), keeping `pet/` portable. `closest('section')` was the second half of the bug: it is a TYPE selector, so it matched `<section id="hero">` but never `<footer id="footer" class="section footer">` — a `<footer>` tag that merely carries a `section` CLASS. Even handed the footer headline it would have fallen through to the headline's parent `div`. Matching a class like `.section` would have fixed this demo and broken portability, which is exactly the trade the original comment set out to avoid. (4) **Exactly ONE live zone, always the active home's** — R8-1's "one caret at Byte's home" applied to the clickable area: feeding stays scoped to where Byte actually lives, rather than binding both homes at once and letting a visitor toss a glyph into a region Byte cannot reach. (5) **Out of scope, flagged not fixed:** the keyboard "Feed Byte" button (`.hero__feed-key`, R9-2) still lives only in the hero, so a keyboard/AT visitor at the footer has no feed affordance. That is a PAGE concern (`index.html`/`main.ts`), not a `pet/` portability one, and belongs in its own change beside a footer twin of the reveal-on-focus button. **No new deps; no page-side change.** **261 tests** (+7 vs D-19's 254).
**Why:** the zone had to become a function of the active home because that is what it always meant — "the area you can click to feed Byte" is only coherent relative to where Byte is — and freezing it at construction quietly made the entire T8 footer-migration feature unreachable by pointer, the demo's primary interaction, on the one screen where the FED counter is visible. Extracting the derivation buys a real regression test for the `<footer class="section">` case that no amount of `createBytePet` integration testing would have caught cheaply. **QA:** full `vitest` **261 passed / 17 files**, `tsc --noEmit` (strict) clean, `eslint .` clean, `prettier --check .` clean, `vite build` clean at **208.99 KB gz** JS (budget 280). Verified in-browser against the dev server by patching `add`/`removeEventListener` before boot: at boot exactly one pet listener, on `section#hero.hero`; on the switch to the footer home, `REMOVE section#hero.hero` → `ADD footer#footer.section.footer`; switching back, `REMOVE footer` → `ADD hero`; a redundant switch logs nothing; `destroy()` leaves none behind. Behaviourally, BEFORE the fix three real footer clicks with Byte homed at the footer produced zero hero-listener hits and left the counter at **FED 0** (while one hero click gave **FED 1**); AFTER, one real footer click takes it **FED 0 → FED 1**. The home switch was driven through the pet's own `setHomeAnchor` — the exact call `runMigrationFull`'s arrival branch makes — rather than a scroll-driven migration, because the session's Browser pane freezes rAF when unfocused (the D-18/D-19-documented limitation) and the GSAP ticker that drives the entrance, the travel lane and the band check cannot run there; **a scroll-driven pass on a real machine remains the cheap owner confirmation.**

## D-19 · T11 first-visit cursor messaging: serialize the sound gate ahead of ALL zone pills via a root-state CSS gate — 2026-09-01
**Choices:** (1) **The fix is a root-level CSS gate, NOT a cursor change.** `page/hero.ts`'s `initSoundControls` now carries a `.byte-sound-locked` boolean state class on `document.documentElement` while the audio gate is shut — the exact idiom `lib/cursor.ts` already uses for `.byte-cursor-active` — and `global.css` hangs one rule off it: `.byte-sound-locked .byte-cursor__pill { display: none; }`. **`src/lib/cursor.ts` and `src/main.ts` were NOT modified**: the cursor stays a blind dot→pill mechanism and `main.ts`'s `resolveCursorLabel` stays the SOLE zone→label authority (**R7-4 preserved, not re-litigated**). Verified in-browser: pre-unlock the resolver still resolves `FEED`/`OPEN`/`TOGGLE` and still clears the pill's `hidden` attribute exactly as before — only the computed `display` changes — so the suppression is provably invisible to the zone layer. (2) **ALL pills, not just `FEED`** (the ticket's load-bearing call): the collision is that the first-gesture unlock is a capture-phase `pointerdown` on `window`, so EVERY zone's pill describes the same single click as the gate hint, ~18px away. Suppressing `FEED` alone merely relocates the collision to `OPEN` and `TOGGLE` (enumerated in-browser: with `scope=feed`, any link and the theme/EQ buttons still show two simultaneous cursor messages) and — since CSS cannot know which label the pill currently holds — would force exactly the `hero.ts`→`main.ts` coupling R7-4 rejected. (3) **Placed AFTER `initSoundControls`'s `if (!button) return` guard**: a stripped page with no EQ button builds no gate hint and attaches no unlock listener, so setting the flag there would suppress every cursor pill permanently. This is a real regression the 4th unit test catches — mutation-verified by moving the `classList.add` above the guard and watching that test, and only that test, fail. (4) **Cleared in `handleFirstGesture` alongside `removeGateLabel()`**, so pointer AND keyboard unlock both restore the pills (SPEC §12 keyboard parity — a keyboard-only visitor never fires `pointerdown` and must not lose the pills for the session). (5) **Touch/coarse is unaffected by construction:** `initCursor()` builds no pill DOM on a coarse pointer (R7-5), so the rule is inert there, and the gate hint keeps its `--static` corner variant. (6) **Out of scope by owner decision:** `createBytePet.ts`'s `(click to feed Byte)` invited hint stays as-is — it is page copy anchored under the headline, not a cursor label, so it never stacks with the gate; and it is retired by `markHintPermanentlyDismissed()` on the *feed action*, not on being seen, so hiding it pre-unlock would permanently destroy the affordance for any visitor whose first click lands in the hero. Its post-unlock redundancy with the `FEED` pill is pre-existing and untouched. **No new deps; no `src/pet/*` change.** **254 tests** (+4 vs T10's 250).
**Why:** the two messages were never a cursor bug — the cursor was right, the gate was right, they were simply concurrent — so the fix belongs at the layer that owns "which of these two may speak", which is the document's own state, not either mechanism. Expressing that as a root-state class + one CSS rule keeps the serialization declarative and zone-blind: `cursor.ts` stays a mechanism, `main.ts` stays the single label authority, and the whole behaviour is one class toggle whose lifecycle (set on init · cleared by pointerdown · cleared by keydown · never set with no EQ button) is unit-testable without a browser. Written test-first (the four flag-lifecycle tests in `hero.sound.test.ts` failed first for the right reason; the negative no-EQ-button guard was mutation-verified since it cannot fail pre-implementation). **QA:** full `vitest` **254 passed / 16 files**, `tsc --noEmit` (strict) clean, `eslint .` clean, `prettier --check .` clean; in-browser on a fine pointer, pre-unlock shows the gate hint with `display: none` pills in ALL FOUR zones (hero / link / toggle / elsewhere) and post-unlock shows the hint gone with pills resumed in every zone. The before/after hero stills were captured in the session's Browser pane, whose `visibilityState: hidden` freezes rAF (the D-18-documented limitation): the pill's paint/label state in both stills is genuine unmodified page state, while the pointer-follow transforms and the entrance-typed headline were stood in by hand because GSAP cannot tick there — an owner eyeball on a real fine pointer remains the cheap confirmation. SPEC amended per the owner-pinned wording: **§8.3** gains "the cursor's zone pills stay suppressed until that gate opens, so a first-time visitor sees exactly one cursor message" and **§8.7** qualifies the pills as "post-unlock only — see §8.3". **T11→DONE; branch stays OPEN** (unchanged from D-18 — still held for T-GLB / T-Audio).

## D-17 · T9 hardening: pure-throttle announcer (pre-created polite region), reveal-on-focus keyboard feed via a unified wake-then-feed, live reduced-motion self-detect, per-tick Color hoist, ≥44px touch targets — 2026-08-27
